# План разработки Telegram-бота

Статус: **план, код бота ещё не написан**. Бэкенд под него подготовлен —
таблица `leads_telegramsubscriber` уже есть в БД (`webapp/backend/leads/models.py`).

## 1. Зачем бот нужен (3 сценария)

1. **Выдача лид-магнита.** Кнопка «Подписаться в Telegram» на сайте (Главная,
   Услуги, Блог, О мне — компонент `CtaDark`) сейчас ведёт в никуда (`href="#"`).
   По плану — это deep-link вида `https://t.me/<bot_username>?start=wardrobe_guide`.
   Бот по команде `/start wardrobe_guide` присылает PDF-гайд «Как разобрать
   гардероб самостоятельно» и сохраняет подписчика в `TelegramSubscriber`.
   Это самый безболезненный способ выдать лид-магнит без формы и валидации
   номера телефона (альтернатива с вводом номера, описанная в Диз-доке,
   отклонена в пользу этого варианта — меньше трения для пользователя).

2. **Уведомление Альбины о новых заявках.** Когда на сайте появляется новая
   заявка (`Lead`, модель уже есть в `webapp/backend/leads/models.py`) — бот
   должен прислать Альбине сообщение в личку с именем, телефоном и услугой.
   Технически: Django-сигнал `post_save` на `Lead` → бот отправляет
   `sendMessage` на её `chat_id` (нужно получить один раз, когда она напишет
   боту `/start` как админ).

3. **Рассылка подписчикам.** Формат ещё не определён заказчиком (см. Диз-док:
   "формат самой рассылки пока не определён") — это открытый вопрос ниже,
   пока не проектирую конкретный UI для рассылок, только модель данных,
   которая это переживёт (`TelegramSubscriber.is_active` уже есть для будущего
   opt-out).

**Не входит в MVP:** сам бот НЕ обрабатывает бронирование услуг (это делают
кнопки "Записаться"/"Заказать капсулу" и т.п. — они пока тоже ведут на
`#footer-contacts`, отдельная задача завести настоящую форму → `POST /api/leads/`,
API для этого уже готов).

## 2. Архитектура

Отдельный процесс на Python, **использующий Django ORM в standalone-режиме**
(`django.setup()` + `DJANGO_SETTINGS_MODULE=config.settings`), а не отдельная
БД/API-клиент. Плюсы: модели/миграции одни на двоих с бэкендом, не нужно
дублировать доступ к Postgres или городить HTTP между ботом и Django.
Минус: бот должен жить в том же venv (или venv с доступом к Django-коду) —
не проблема, сервер уже развёрнут под Django (`/var/www/albina/venv`, см.
project memory про провижининг).

```
webapp/
  backend/        # Django (уже есть)
  bot/            # новый пакет, НЕ Django-приложение
    __init__.py
    main.py       # точка входа: django.setup() + запуск aiogram Dispatcher
    handlers.py   # /start, deep-link с параметром, обработка сообщений
    notifications.py  # функция notify_new_lead(lead), вызывается из Django-сигнала
    requirements.txt  # aiogram (+ то, что нужно от Django/psycopg — уже есть в backend/requirements.txt)
```

Библиотека: **aiogram 3.x** (асинхронный, активно поддерживается, стандарт
де-факто для новых Telegram-ботов на Python в 2026).

Связь Django → бот: сигнал в `webapp/backend/leads/models.py` или
`leads/signals.py`:

```python
@receiver(post_save, sender=Lead)
def on_lead_created(sender, instance, created, **kwargs):
    if created:
        notify_new_lead.delay(instance.id)  # или прямой вызов, если без очереди
```

Для MVP — без брокера очередей (Celery/Redis избыточны для одного уведомления
в личку); прямой синхронный вызов Telegram Bot API из сигнала приемлем при
такой нагрузке (сайт с несколькими заявками в день). Если появится нужда в
очереди — это отдельная задача, не блокирует MVP.

## 3. Запуск: polling vs webhook

**MVP — long polling.** Не требует публичного HTTPS-эндпоинта, не завязан на
Nginx-конфиг, проще для старта и локальной разработки. Дальше, если понадобится
(экономия ресурсов на VPS с 2 ГБ RAM — polling держит процесс активным
постоянно) — перейти на webhook через уже настроенный Nginx на сервере.

Деплой на сервере — отдельный systemd-unit (сервер уже готов: Nginx/venv на
`/var/www/albina`, см. project memory), например `albina-bot.service`,
`Restart=on-failure`, читает токен из того же `.env`, что и Django.

## 4. Модель данных

`TelegramSubscriber` уже создана в этой сессии (`webapp/backend/leads/models.py`):
`chat_id`, `username`, `first_name`, `source` (deep-link параметр), `is_active`,
`subscribed_at`. Этого достаточно для сценариев 1 и 3 выше.

Для сценария 2 (уведомление Альбины) — её `chat_id` нужно где-то хранить.
Не заводить отдельную модель ради одной записи — положить в `SiteProfile`
(уже singleton для профиля сайта) поле `owner_telegram_chat_id`, заполнить
один раз через админку, когда она напишет боту.

## 5. Что нужно от заказчика (открытые вопросы)

1. **Создать бота через @BotFather**, прислать токен (`TELEGRAM_BOT_TOKEN`,
   хранить в `.env`, никогда не коммитить — по аналогии с `SECRET_KEY`).
   Придумать username бота — он же попадёт в deep-link на сайте.
2. **Сам файл PDF-гайда** — контента для него достаточно (флоучарт "выбросить
   / подарить / в химчистку-ателье / оставить в шкафу / коробка с памятными
   вещами", присланный в чате), но самого PDF-файла ещё не существует. Можно
   собрать через ту же технику, что уже использовалась для Мудборд.pdf —
   HTML/CSS → Playwright `page.pdf()` (см. project memory "Как делать PDF в
   этом окружении").
3. **Формат рассылки** — не определён (см. Диз-док). Не проектирую эту часть
   бота, пока не будет ответа.
4. Хочет ли Альбина, чтобы бот уведомлял её о заявках **лично ей**, или нужен
   отдельный чат/канал для команды (если появятся помощники)?

## 6. Этапы реализации

1. `pip install aiogram` в `webapp/backend/.venv` (или отдельный venv — решить
   при реализации), добавить `TELEGRAM_BOT_TOKEN` в `.env.example`.
2. `bot/main.py` с `/start` (без параметра — приветствие + кнопка "Получить
   гайд"; с параметром `wardrobe_guide` — сразу шлёт файл), сохранение в
   `TelegramSubscriber`.
3. Загрузить сам PDF (см. п.5.2) — как файл в `MEDIA_ROOT` или прямо в код
   бота (`send_document`).
4. Сигнал `post_save` на `Lead` → `notify_new_lead` (нужен `owner_telegram_chat_id`
   в `SiteProfile`, см. п.4).
5. Подключить реальный `href` на кнопках "Подписаться в Telegram" /
   "Написать в Telegram" на фронтенде (`CtaDark.jsx`, `Footer.jsx`,
   `ServiceDetailPage.jsx`) вместо текущих `#`-заглушек.
6. Локальный прогон (polling), затем деплой на VPS как systemd-unit.
7. (Опционально, после MVP) переход на webhook через Nginx.

## 7. Безопасность

- Токен бота — только в `.env`, по аналогии с `SECRET_KEY`/`DATABASE_URL`
  (см. `.gitignore` в `webapp/backend/` и в корне репозитория — `.env`
  уже исключён отовсюду).
- `chat_id` Альбины (владельца) — не публиковать, не логировать в открытом
  виде.
